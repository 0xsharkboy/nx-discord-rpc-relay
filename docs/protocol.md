# Relay HTTP protocol (v1)

This is the contract between the Switch sysmodule and the relay. The relay links a Discord account
to a console through the OAuth device flow, then turns the console's presence reports into Discord
Rich Presence.

## Conventions

- Base URL: the relay's public URL, for example `https://nx-discord-rpc.0xsharkboy.dev`. Every path below is
  relative to it.
- Request and response bodies are JSON (`Content-Type: application/json`), except icon uploads
  (raw JPEG bytes), icon downloads (`image/jpeg`) and `GET /healthz` (`text/plain`).
- Every request with a body must send `Content-Length`. Chunked uploads
  (`Transfer-Encoding`) are refused with `411 length_required`. A request without `Content-Length`
  is treated as having an empty body.
- The relay may close the connection after any response (it sends `Connection: close` on the hop
  it controls), and keep-alive through the public endpoint is not guaranteed. Clients must handle a
  closed connection and should simply open one connection per request, never relying on keep-alive.
- Any request body over 262144 bytes is discarded unprocessed and refused with `413 too_large`,
  before authentication or any other check except `426 client_outdated` (see
  [Client version](#client-version)).
- Lengths are counted in bytes of UTF-8, not characters.
- Unknown JSON fields in request bodies are ignored. Clients must ignore unknown fields in
  responses.

### Authentication

Keyed routes take the API key returned by the link flow:

```
Authorization: Bearer <api_key>
```

The API key is 43 characters of base64url. Store it; the relay keeps only its hash and cannot show
it again. A missing, malformed or unknown key gives `401 unauthorized`.

### Client version

The console sends its version in every request:

```
User-Agent: nx-discord-rpc/<X.Y.Z>
```

`X.Y.Z` is three decimal numbers, compared numerically (`0.10.0` is newer than `0.9.1`).

A relay may set a minimum console version (`MIN_CLIENT_VERSION`, unset on the official relay). On
every `/v1/` route except `DELETE /v1/me`, a request whose User-Agent is exactly
`nx-discord-rpc/<X.Y.Z>` with a version older than that minimum gets `426 client_outdated`, before
any other check (authentication, body, rate limits, even an unknown route):

```json
{"error": "client_outdated", "message": "<human readable text>", "min_version": "0.6.0"}
```

`min_version` is the oldest version the relay serves. Any other User-Agent, including ours with a
version that is not `X.Y.Z`, is served as usual: third-party clients are never refused for their
User-Agent. `GET /healthz` and `GET /icons/...` are never refused, and neither is
`DELETE /v1/me`, so any console can always unlink and delete its data.

### Errors

Every error response, including `404` for an unknown route, has this body:

```json
{"error": "<code>", "message": "<human readable text>"}
```

Clients must branch on `error`, never on `message`.

| Status | `error` | Meaning |
|---|---|---|
| 400 | `invalid_body` | `PUT /v1/presence` body failed validation |
| 400 | `invalid_icon` | Not a 256×256 JPEG, or the title id is invalid |
| 400 | `blocked` | This exact image was removed by an admin |
| 400 | `bad_request` | Malformed HTTP request |
| 401 | `unauthorized` | Missing, malformed or unknown key (or admin key required) |
| 404 | `unknown_link` | The `link_id` was never issued or is gone |
| 404 | `not_found` | Unknown route, or no such icon |
| 405 | `method_not_allowed` | Method not allowed |
| 409 | `link_broken` | The Discord authorization was revoked or can no longer be refreshed |
| 411 | `length_required` | Chunked request body |
| 413 | `too_large` | Body over the route's limit |
| 414 | `uri_too_long` | Request line too long |
| 416 | `range_not_satisfiable` | Malformed or unsatisfiable `Range` header |
| 426 | `client_outdated` | The console is older than the relay's minimum version, see [Client version](#client-version) |
| 429 | `rate_limited` | Too many requests; see `Retry-After` |
| 500 | `internal_error` | Relay fault |
| 502 | `discord_unavailable` | Discord did not answer; retry later |
| 503 | `storage_full` | The relay stores no new icons for now |
| other | `http_<status>` | Generated by the HTTP layer, for example `http_417` |

### Client behavior

- **401** on a keyed route: the key is dead (the account was unlinked, or relinked from another
  console). Stop sending presence and offer to link again. An account with no accepted
  `PUT /v1/presence` for 90 days is deleted by the relay, so its key also gets `401` and the console
  must link again.
- **409 `link_broken`**: stop sending presence and offer to link again. `GET /v1/me` reports
  `link_broken: true` in this state.
- **429** and **5xx**: back off. When `Retry-After` (seconds) is present, wait at least that long;
  otherwise use exponential backoff starting at 5 s, capped at 5 min.
- **426 `client_outdated`**: the console must be updated to `min_version` or newer. Tell the user
  and stop sending presence and icons. Retry one presence request every 6 hours, since the
  operator may lower the minimum; a retry that meets a network error, a 429 or a 5xx backs off as
  usual. Requests the user asks for, such as linking or unlinking, are still sent; `DELETE /v1/me`
  is never refused.
- Network errors: same as 5xx.
- **404 `unknown_link`** while polling: the relay forgot the link, for example because it restarted
  (pending links live in memory only). Start again with `POST /v1/link`.
- Any other **4xx**, including a code this document does not list: treat the request as failed and
  do not retry it unchanged. Back off on any **5xx**.

## Compatibility policy

- Changes inside `/v1` stay backward compatible: only new optional fields and new answers. A
  console of any release keeps working with the current relay.
- A breaking change ships as `/v2/` routes in a homebrew release. `/v1` keeps working for at least
  3 months after that release, and this is announced in the release notes.
- Only then may the operator set `MIN_CLIENT_VERSION` to the first release that speaks `/v2`, after
  checking the daily client version counts in the relay log (see
  [self-hosting.md](https://github.com/0xsharkboy/nx-discord-rpc-relay/blob/main/docs/self-hosting.md#9-client-versions)).
  Consoles older than that minimum then get `426 client_outdated`. From v0.6.0, a refused console
  shows that an update is required. Consoles v0.5.0 and older do not know this answer: their
  presence only stops showing on Discord, their Status tab still says Linked and relay OK, Test
  connection reports "The relay refused the last update (error 426)", and linking again says
  "Something went wrong". They can still unlink. Raise the minimum only once the daily counts show
  few consoles older than v0.6.0.

## Rate limits

| Route | Limit | Key |
|---|---|---|
| `POST /v1/link` | 10 per hour | client IP |
| `POST /v1/link/{link_id}/poll` | 720 per hour | client IP |
| `PUT /v1/icons/{title_id}` | 30 per hour | API key (the admin key is exempt) |
| `PUT /v1/icons/{title_id}`, new images only | 50 per day | API key (the admin key is exempt) |

IPv6 clients are counted per /64 prefix.

Limits are token buckets: the full allowance is available at once, and one request comes back
every hour / limit (every 6 min for `POST /v1/link`). A refused request gets
`429 rate_limited` with `Retry-After: <seconds>`.

The daily icon limit counts only uploads that store a new image (bytes the relay did not have yet).
It is also a token bucket: 50 new images at once, then one more every 24 h / 50 (about 29 min).
It is held in memory only, keyed by the API key's hash, so that one account cannot fill the
relay's icon storage for everyone.

## Presence timing

- **Heartbeat:** while a title runs, `PUT /v1/presence` every 60 s, and immediately when the title,
  name or details change.
- **Timeout:** the relay clears the presence after 150 s without a `PUT`. A console that loses
  Wi-Fi or sleeps therefore drops off Discord on its own.
- **Updates:** the relay sends at most one change to Discord every 5 s per account. When several
  `PUT`s arrive within that window, the latest wins; none are queued. Repeating an identical state
  costs nothing.
- **Elapsed time:** `elapsed_s` is how long the title has been running, as measured by the console.
  The relay computes the start as `relay_now - elapsed_s`, so the console's clock does not need to
  be right. Send the current value on every heartbeat. Omit it to show no timer.
- **Stopping:** send `DELETE /v1/presence` when the title closes, rather than waiting for the
  timeout.

## Title ids

A title id is 16 hexadecimal digits, either case, with a value of at least `0100000000010000`
(so `0000000000000000` is invalid). The relay normalizes it to upper case.

## Routes

### `POST /v1/link`

Starts linking. No auth, no body.

**200**

```json
{
  "link_id": "q3hJ1Wc0p1n3Yb2mY0dZ8g",
  "user_code": "ABCD-EFGH",
  "verification_uri_complete": "https://discord.com/activate?user_code=ABCD-EFGH",
  "expires_in": 300,
  "interval": 5
}
```

Show `user_code` and `verification_uri_complete` (for example as a QR code) to the user, who
approves the request on another device. Then poll every `interval` seconds until a final state or
`expires_in` seconds have passed. Keep `link_id` private: whoever polls with it receives the API key.

Errors: `429 rate_limited`, `502 discord_unavailable`.

### `POST /v1/link/{link_id}/poll`

No auth, no body.

**200**, one of:

```json
{"state": "pending"}
{"state": "denied"}
{"state": "expired"}
{"state": "linked", "api_key": "Zk3...43 chars...", "username": "alice"}
```

- `pending`: keep polling every `interval` seconds. Polling faster is harmless but only returns
  `pending`.
- `denied`: the user refused. Final.
- `expired`: the code expired. Final; start again with `POST /v1/link`.
- `linked`: store `api_key`. Final. Polling again within 60 s returns the same key, so a response
  lost to a dropped connection can be fetched again; after that the link answers `expired`.

Linking a Discord account that is already linked replaces its key: the previous key stops working
at once.

Errors: `404 unknown_link` (never issued, forgotten some time after it ended, or lost to a relay
restart: start again with `POST /v1/link`), `429 rate_limited`,
`502 discord_unavailable` (retry the poll later).

### `GET /v1/me`

Auth: API key.

**200**

```json
{"username": "alice", "link_broken": false, "presence": {"name": "Zelda", "details": "Chapter 1"}}
```

`presence` is the activity last sent to Discord, or `null` when none is shown.

Errors: `401 unauthorized`.

### `DELETE /v1/me`

Auth: API key. Unlinks the account: the key stops working at once, the presence is cleared, and the Discord
authorization is revoked a few seconds later in the background (best effort: a revocation not yet
sent when the relay stops is dropped).

**204**, no body. Errors: `401 unauthorized`. Never refused with `426 client_outdated`, whatever
the console's version (see [Client version](#client-version)).

### `PUT /v1/presence`

Auth: API key. Body (at most 4096 bytes):

```json
{"name": "The Legend of Zelda", "details": "Chapter 1", "elapsed_s": 754, "title_id": "0100A0D02127E000",
 "icon": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"}
```

| Field | Type | Rule |
|---|---|---|
| `name` | string | Required, 1–128 bytes. Shown as the activity name and the image tooltip. |
| `details` | string | Optional, 0–128 bytes. Absent or `null` means empty. |
| `elapsed_s` | integer | Optional, 0–31536000. Floats, booleans and strings are refused. |
| `title_id` | string | Optional, a valid title id. Matches an icon upload to the current title. |
| `icon` | string | Optional, 64 lowercase hex characters: the SHA-256 of the raw JPEG bytes of the title's icon. Anything else is refused with `400 invalid_body`. `null` counts as absent. |
| `badge` | boolean | Optional. `true` adds the NX Discord RPC badge to the presence: a small image over the game icon (`/badge.png`), the tooltip "NX Discord RPC", and a link opened by a click (`BADGE_URL` on the relay, by default the project page). Absent, `null` or `false`: no badge. Anything else is refused with `400 invalid_body`. |

`name` and `details` are shown exactly as sent. `null` counts as absent for the optional fields.
The image is chosen in this order: the icon named by `icon` when the relay stores it, then an icon
published for the title before v0.4.0 (see [Legacy title icons](#legacy-title-icons)), then the
Switch logo.

**204**, no body, when the body has no `icon`.

**200** when the body has an `icon`:

```json
{"need_icon": true}
```

`need_icon` is `true` when the relay does not store that hash and wants the image, and `false` when
it does. It is also `false` when an admin removed the hash: the relay then ignores it and shows the
Switch logo (or a legacy icon), and there is nothing to upload. When the relay stores the hash, it
records the use. A relay older than v0.4.0 answers `204` to every presence.

Errors, checked in this order: `401 unauthorized`, `409 link_broken`, `413 too_large` (body over
4096 bytes), `400 invalid_body` (not a JSON object, or a field breaks a rule). A body over the
global 262144-byte limit gets `413` before any of these.

### `DELETE /v1/presence`

Auth: API key. Clears the presence now. No body.

**204**, no body. Errors: `401 unauthorized`.

### `PUT /v1/icons/{title_id}`

Auth: API key, or the admin key. Body: the raw icon bytes (`Content-Type: image/jpeg`).

Rules:

- The body is at most 131072 bytes and is a baseline or progressive JPEG of exactly 256×256 pixels.
  The relay re-encodes it before serving it.
- The relay names the file after the SHA-256 of the bytes as uploaded (64 lowercase hex characters),
  never after the re-encoded image. The same bytes always give the same hash, whoever uploads them
  and for whichever title.
- The title id in the path must be valid. It is not stored: it only tells the relay which title
  the icon belongs to. When the uploading account is showing that title, its presence switches to
  the uploaded icon at once, which is how a console that does not send `icon` gets its image. An
  upload for another title only stores the file.
- Storing an image that is already stored is not an error.
- The relay keeps at most 10000 icon files. Past that, new images are refused with
  `503 storage_full`.
- An account stores at most 50 new images per day (see [Rate limits](#rate-limits)). Past that, an
  upload of an image the relay does not have yet is refused with `429 rate_limited` and
  `Retry-After`, and nothing is stored. Images already stored are accepted as before.
- Uploads with the admin key are stored the same way and are not rate limited. They do not change
  anyone's presence.

Responses:

| Status | Body | Meaning |
|---|---|---|
| 200 | `{"status": "stored"}` | The image is stored (or already was) |
| 400 | `invalid_icon` error | Not a 256×256 JPEG, or the title id is invalid |
| 400 | `blocked` error | An admin removed this exact image |
| 413 | `too_large` error | Body over 131072 bytes |
| 503 | `storage_full` error | The relay stores no new icons for now |

Other errors: `401 unauthorized`, `429 rate_limited`.

### `DELETE /v1/icons/{hash}`

Auth: admin key. Blocks the image with this hash, so the same bytes cannot be stored again, and
deletes its file. Presences that showed it switch to the Switch logo. No body.

**204**, no body. Errors: `401 unauthorized` (missing or non-admin key), `404 not_found` (the hash
is unknown and already blocked, or the title id has no legacy icon). A path that is not a valid hash is
treated as a title id.

`DELETE /v1/icons/{title_id}` still works for an icon published before v0.4.0 (see
[Legacy title icons](#legacy-title-icons)): it unpublishes that icon and blocks its image. A path
that is a valid hash is always treated as a hash.

### `GET /icons/{hash}.jpg`

No auth. Serves a stored icon; this is the URL Discord loads. Anyone who knows a hash can load its
image.

**200** with `Content-Type: image/jpeg` and `Cache-Control: public, max-age=86400`.

Errors: `404 not_found` (not a valid hash, not stored, or blocked).

### Legacy title icons

Before v0.4.0 icons were published by title and served at `GET /icons/{title_id}.jpg`. The relay
still serves them, read-only, so existing links keep working, unless an admin blocked the image
(the route then answers `404`). They are used only when a presence has no usable `icon`. Nothing
new is published by title.

### Console behavior for icons

A console that sends `icon` follows these rules:

- Upload the icon with `PUT /v1/icons/{title_id}` only when the relay answers `need_icon: true`.
- After a `200` upload, upload again only after a later `need_icon: true`, and at most once per 10
  minutes per title.
- After a network error or a `5xx` (including `503 storage_full`), retry after 1, 5 and 15 minutes,
  then every 15 minutes.
- After a `400` (`invalid_icon` or `blocked`) or a `413` (`too_large`), stop uploading that title for the
  session.
- When a presence with `icon` gets `204`, the relay is older than v0.4.0 and does not use hashes:
  upload the icon once per title per session, as before.

A console from before v0.4.0 sends no `icon`, gets `204`, and uploads its icon once after its first
presence for a title. The relay attaches that upload to the account's current presence.

### `GET /badge.png`

No auth, never refused. The badge image (PNG) used as the small image of presences that ask for the
badge. **200** with `Content-Type: image/png` and `Cache-Control: public, max-age=86400`.

### `GET /healthz`

No auth. **200** with the text body `ok`.

## Examples

Link:

```
POST /v1/link HTTP/1.1
Host: nx-discord-rpc.0xsharkboy.dev
Content-Length: 0

HTTP/1.1 200 OK
Content-Type: application/json

{"link_id":"q3hJ1Wc0p1n3Yb2mY0dZ8g","user_code":"ABCD-EFGH","verification_uri_complete":"https://discord.com/activate?user_code=ABCD-EFGH","expires_in":300,"interval":5}
```

Heartbeat:

```
PUT /v1/presence HTTP/1.1
Host: nx-discord-rpc.0xsharkboy.dev
Authorization: Bearer Zk3...
Content-Type: application/json
Content-Length: 98

{"name":"The Legend of Zelda","details":"Chapter 1","elapsed_s":754,"title_id":"0100A0D02127E000"}

HTTP/1.1 204 No Content
```

Broken link:

```
HTTP/1.1 409 Conflict
Content-Type: application/json

{"error":"link_broken","message":"The Discord link is broken, link the account again"}
```

Rate limited:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 360
Content-Type: application/json

{"error":"rate_limited","message":"Too many requests, retry later"}
```
